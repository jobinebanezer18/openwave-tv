# OpenWave platform distribution plan

Status: planning draft, 12 October 2026. Owner decisions: **India first; curated guide plus private, user-supplied playlists; direct website/GitHub distribution only; no App Store or Play Store release.** Recheck linked platform rules before each release. This document covers ordinary, unmodified devices; it does not authorize publishing, purchasing accounts, or claiming rights to any feed.

## Decision in one page

| Platform | First public route | Later route | Main gate |
| --- | --- | --- | --- |
| iPhone and iPad in India | Hosted HTTPS web app added to Home Screen from the project website | No native iOS direct-download release in the India-first plan | The present localhost Go server cannot be installed as a website; redesign media delivery and validate sources first. Apple does not currently offer a general native `.ipa` website-install route in India. |
| Android in India | Hosted web app, then signed APK from the project website or verified GitHub release | No Play Store listing in this plan | Stable signing key, mobile playback, Android developer verification as rollout expands. |
| macOS | Existing GitHub release for technical testers | Developer ID signed, hardened-runtime, notarized `.dmg` or `.pkg` | Apple Developer Program and notarization; clean launch under Gatekeeper. |
| Windows | Existing GitHub release for technical testers | Authenticode signed installer or signed MSIX; `winget` listing after installer stabilizes | Publisher identity, trusted certificate, update and uninstall behavior; initial SmartScreen reputation. |
| Linux | Existing GitHub release | AppImage, then optional Flathub | Portability across supported distributions, desktop integration, sandbox/portal behavior. |

**The iPhone deliverable for India is a Home Screen web app, not a native `.ipa`.** An `.ipa` posted to GitHub cannot be installed by arbitrary users on ordinary Indian iPhones. Apple's [distribution overview](https://developer.apple.com/distribute/) identifies alternative native distribution only in specific regions, and its [website distribution rules](https://developer.apple.com/documentation/marketplacekit/distributing-your-app-from-your-website) limit non-marketplace app installation from a website to the EU. Safari supports adding a website as a Home Screen app ([Apple's iPhone guide](https://support.apple.com/guide/iphone/open-as-web-app-iphea86e5236/27/ios/27)). This is a product constraint, not a missing build step.

## Current project baseline

The repository currently builds a Vite frontend into an embedded Go executable. The Go process binds to `127.0.0.1`, fetches channel catalogs, creates playback sessions, and proxies HLS media to the browser; the README states that local server is required. GitHub Actions builds unsigned executable archives for Linux `amd64/arm64`, macOS `amd64/arm64`, and Windows `amd64`. There is no mobile package, publicly hosted backend, service worker, installable manifest, updater, signing workflow, or native mobile playback implementation. This is a useful desktop prototype, not a production install experience.

**Architecture gate before mobile packaging:** choose and prototype one supported media path:

1. **Hosted HTTPS service + web app:** route to ordinary iPhones and Android phones. Prefer direct viewer-to-broadcaster media to keep static hosting free. If a relay is proposed, first check source terms, proxy abuse controls, bandwidth budget, regional access behavior, and privacy boundaries. Do not expose the current session API publicly unchanged.
2. **Direct broadcaster URLs where permitted:** avoids paying to relay media, but many feeds require headers, block browser cross-origin access, or fail due to mixed content. Support only after measuring real-device success by broadcaster and browser.
3. **Device-local service in a native shell:** closest to the desktop architecture, but background execution, local network permissions, app lifecycle, audio focus, and iOS review/distribution need proof on physical devices. Treat as research, not the default roadmap.

Decision record to complete: measure 50 representative TV feeds and 30 radio feeds across iPhone Safari, Android Chrome, macOS Safari/Chrome, and Windows Edge. Record direct-play success, codec, latency, bandwidth, failure reason, and whether a proxy was necessary. Choose the simplest lawful path that reaches a declared launch reliability target; keep the catalog and UI shared either way.

## iOS and iPadOS

### Home Screen web app, worldwide

Ship the app at a stable HTTPS origin with a Web App Manifest, icons, `display: standalone`, correct safe-area/mobile video behavior, and a service worker that caches only the application shell and permitted metadata. Explain “Add to Home Screen” in an optional install affordance after the viewer has tried playback; never imply it is an App Store app. WebKit documents [Home Screen web apps](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) and says that on iOS/iPadOS 26 any site can be added as a web app, while a manifest still supplies identity and icons ([WebKit 26 notes](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)). Live video still needs network connectivity. Do not cache or redistribute stream segments offline without broadcaster permission.

Acceptance: on two supported iPhone sizes and an iPad, install from Safari; reopen from icon; onboarding and favorites persist; HLS starts by explicit tap; switching TV/radio, background audio, rotation, captions when present, and recovery after connection loss work; no local-server setup is shown to the user.

### Native outside Apple's store: excluded from the India-first release

The EU permits notarized apps through authorized alternative marketplaces and, for developers Apple approves, direct Web Distribution from a registered site. Apple expanded eligibility in October 2026, but Web Distribution still requires meeting one of several qualifications (for example financial stability review, public company/venture funding/audit, qualifying nonprofit, substantial letter of credit, or one million first annual installs) and Apple authorization. A new solo project must **not** assume approval ([Apple EU support](https://developer.apple.com/support/apps-in-the-eu)). Japan supports alternative marketplaces on iOS 26.2+ and Brazil on iOS 26.5+; Apple’s regional documentation says ordinary apps in those markets distribute through marketplaces, while only the marketplace app itself installs from a website ([Apple regional rules](https://developer.apple.com/documentation/marketplacekit/participating-in-alternative-distribution-for-specific-regions)). Other regions should be offered the web app unless Apple adds a supported channel. Apple notarizes alternative-distribution apps and checks functionality, safety, security, and privacy ([Apple EU support](https://developer.apple.com/support/apps-in-the-eu)).

These regional options do not solve distribution to ordinary users in India and are **not a planned launch track**. Reconsider native iOS only if the owner changes target region or Apple adds an India-eligible route. Such a decision would need current Apple eligibility, notarization, physical-device installation evidence, and a new budget; the [Apple Developer Program](https://developer.apple.com/programs/whats-included/) lists a USD 99 annual membership (or local currency). No Apple Developer membership is needed merely to publish the India-first Home Screen web app.

Do not plan Enterprise certificates, developer provisioning, or TestFlight as public consumer distribution; Apple describes Enterprise as private employee distribution ([program overview](https://developer.apple.com/programs/)).

## Android

Google explicitly allows a release-ready APK to be hosted on a website; users must opt in to install apps from that source, on Android 8+ through a per-source “Install unknown apps” setting ([Android alternative distribution](https://developer.android.com/distribute/marketing-tools/alternative-distribution)). Build a real Android experience around the shared discovery UI and validated media path. Download only from the project’s official HTTPS domain or verified GitHub release; display package name, version, SHA-256, and publisher identity. Never coach users to disable security globally.

Reserve a stable reverse-domain package ID; create a production signing key in controlled storage; sign and verify every APK; preserve the same signing identity for updates. Android requires installed APKs to be signed, and changing/losing the app signing key breaks normal updates ([Android app signing](https://developer.android.com/studio/publish/app-signing)). Provide an in-app update notice linking to the authenticated release page, or implement a carefully reviewed package installer update flow later. Test install, upgrade, uninstall, background audio, notification controls, picture-in-picture if supported, and devices without Google services.

As of October 2026, Android developer verification has begun for installs from participating stores on certified devices in Brazil, Indonesia, Singapore, and Thailand; India is **not** in this initial enforcement group. Google plans broader coverage of certified devices and apps in 2027, including direct distribution ([official timeline](https://developer.android.com/developer-verification), [distribution paths](https://developer.android.com/developer-verification/guides)). Register the APK's package and signing identity with the Android Developer Console before wide distribution, rather than designing the ordinary-user path around the advanced sideload flow. The owner does **not** need a Google Play Console account for a direct-download APK. Google lists a USD 25 Android Developer Console full-distribution fee; its no-fee limited account covers at most 20 approved test devices ([FAQ](https://developer.android.com/developer-verification/guides/faq), [limited distribution](https://developer.android.com/developer-verification/guides/limited-distribution)).

## Desktop

### macOS

Package a launcher around the current Go server and browser UI only after defining lifecycle: a single instance, a stable loopback origin so browser preferences and favorites persist, a clear port-in-use recovery path, reliable shutdown, menu/dock behavior, crash recovery, and no privileged installation. The current fixed default is `127.0.0.1:8765`; a native shell may later use a stable application-specific origin instead. Sign application and installer with Developer ID, use hardened runtime, submit to Apple’s notary service, staple the result, and test a downloaded artifact on a clean Mac with Gatekeeper. Apple says Developer ID identifies outside-store software to Gatekeeper; notarization adds a review for trusted distribution ([Developer ID](https://developer.apple.com/developer-id/), [notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)). Preserve both Apple silicon and Intel artifacts until support data justifies change. Add a verified updater or clear manual update path, with rollback.

### Windows

Package the current executable as a standard user installer or MSIX, then sign with a trusted publisher certificate. Direct-download MSIX requires a CA-trusted signature; self-signed packages force user trust setup. Microsoft recommends Azure Artifact Signing where eligible, but its availability is region/account limited; use a recognized CA code-signing certificate if unavailable. Initial SmartScreen reputation may still cause prompts even with a valid signature ([Microsoft code signing](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options), [distribution paths](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/choose-distribution-path)). Test installer, uninstall, update, per-user permissions, Windows Defender behavior, firewall prompts, and process cleanup. Publish the signed installer directly on the project website/GitHub; no package-manager listing is in scope. Do not promise warning-free direct downloads.

### Linux

Keep tarballs for technical users. Build a tested AppImage for an easy direct download; publish it on the official release page without wrapping it in another archive, following [AppImage distribution guidance](https://docs.appimage.org/packaging-guide/distribution.html). Include desktop entry, icon, dependency/license notices, executable permissions instructions, and a checksum. Test on representative recent Ubuntu, Fedora, and Debian distributions, X11 and Wayland, `amd64` and `arm64` where feasible. No package-manager or app-store listing is in scope.

## Cross-platform release requirements

These are release gates, not aspirations:

1. **Public catalog policy.** The India-first alpha may list free, publicly accessible streams with a recorded source URL, last playback check, known territory or access limits, and a fast correction/takedown route. Prefer official broadcaster feeds and clearly label third-party indexes; remove sources that are encrypted, paywalled, challenged, or disputed. Written permission for every free link is not a blanket alpha gate, but any proposed relay, reuse of protected artwork, or paid/DRM OTT integration needs its own review. Private user-imported playlists are outside the curated public guide and stay on the viewer's device.
2. **Playback reliability.** Define a measured launch set, not an inflated global channel count. Health checks must sample actual decodable media where possible, identify geo and codec failure separately, expire quickly, and offer a useful alternative. Track success rate by platform, geography, and source. State that live availability is variable.
3. **Security and privacy.** Review the proxy for SSRF, redirect-to-private-network behavior, open relay abuse, rate limits, token expiry, header handling, and bandwidth exhaustion before hosting it. Keep geolocation opt-in and local when possible. Publish a plain privacy notice describing catalog fetches, media requests, optional AI download, and data retention. Do not collect account data until a sync feature requires it.
4. **Accessibility and UX.** Test remote/keyboard/touch navigation, reduced motion, focus order, readable captions when supplied, high contrast, and clear play/retry controls. Keep onboarding once, make country/language settings editable in secondary controls, and show viewer-relevant channel counts only.
5. **Release engineering.** Pin toolchains/dependencies; run frontend, Go, and integration tests; produce a versioned artifact matrix; run dependency/security scans; sign; generate SHA-256 checksums and SBOM; publish changelog and source tag; verify every downloaded artifact on a clean device. Keep signing keys out of the repository and restrict CI release secrets to protected tags with review.
6. **Support and operations.** Provide status/known-feed-issues page, issue template with platform/region/browser/channel, response owner, takedown contact, incident procedure, and rollback plan. Monitor crash-free starts, successful first plays, time to first frame, channel switch time, radio start rate, and per-region failures without storing exact user location.

## Staged execution and exit criteria

| Stage | Work | Exit evidence |
| --- | --- | --- |
| 0. Evidence and architecture | India free-stream provenance and codec sample; decide hosted/direct/local media path; cost envelope; brand/package IDs; device matrix; define private playlist boundaries. | Written architecture decision, public catalog policy, measured playback table, budget owner. |
| 1. Production desktop baseline | Fix launcher lifecycle, package and sign macOS/Windows, AppImage Linux, checksums, CI release gates, clean-machine installs. | Reproducible signed downloads; install/update/uninstall tests; documented rollback. |
| 2. Hosted mobile web beta | HTTPS static deployment with an India-curated direct-play catalog, private on-device playlist import, installable manifest and shell cache, responsive player, consent-based location, mobile QA. | Representative free-stream sample results; first-play and recovery targets met on physical iOS/Android devices. If a media proxy is later chosen, separately review its source terms, security, and load behavior. |
| 3. Android direct APK beta | Native shell or client, stable signed APK, registration, update route, accessibility and device tests. | Verified identity and signing; install/upgrade/uninstall on physical devices; staged public beta with rollback. |
| 4. iOS native feasibility | Deferred outside the India-first plan. Reopen only if Apple establishes an India-eligible direct or marketplace route and the owner requests it. | No India `.ipa` download is advertised; Safari Home Screen install is verified. |
| 5. Public launch | Publish only passing platforms, support/privacy/source-policy pages, issue intake, release notes; monitor metrics and feed reliability. | Launch checklist signed by engineering, product, and catalog owners; 72-hour monitored rollout and rollback trigger. |

Order is deliberate: a native wrapper cannot repair unreliable or unauthorized streams. Stages may overlap in development, but a distribution claim must wait for its own exit evidence. The project owner should decide whether operating a media proxy and pursuing Apple native distribution are worth their cost before committing to them.

## Addendum: a no-cost hosted web beta without video relay

Checked against provider documentation on 12 October 2026. **Recommendation: Cloudflare Pages Free, serving only the static app and a small India-curated catalog on a `pages.dev` HTTPS address.** This no-cost recommendation covers the app shell and metadata only; it never covers an unrestricted media relay. Do not create Pages Functions or a streaming proxy for this phase. Cloudflare states that purely static Pages requests are free and unlimited; Free includes 500 builds per month, 20,000 files, and a 25 MiB limit per file ([static-request pricing](https://developers.cloudflare.com/pages/functions/pricing/), [Pages limits](https://developers.cloudflare.com/pages/platform/limits/)). The service supplies a `*.pages.dev` subdomain after deployment, so a purchased domain is optional ([Cloudflare Pages setup](https://developers.cloudflare.com/pages/framework-guides/deploy-anything/)). These terms make a $0 small beta plausible, but they are platform limits rather than a service-level guarantee.

Functions consume Workers quota if added. | Best fit for static shell/catalog once oversized asset is fixed; avoid Functions and video relay. |

**Current build fails the recommended host’s asset-size gate.** At this audit, `dist/assets/ort-wasm-simd-threaded.asyncify-*.wasm` is **26,861,777 bytes**, while 25 MiB is 26,214,400 bytes. The app is about 31 MB in `dist`; the radio snapshot and city index are each about 1.5 MB and fit. Reduce or replace that optional AI runtime asset, or make an explicit, version-pinned external-hosting decision for it, then check every file in a fresh production build against Pages’ 25 MiB cap. Do not deploy a broken build or remove the natural-language feature without updating its UI promise.

### Static architecture and acceptance gates

1. Build a **mobile web mode** that calls no `localhost` or `/api/*` endpoint. Today `src/main.js` calls `/api/channels` and `/api/session`; those are served by the Go executable, not by static hosting. A direct upload of the current `dist` would render the shell but leave TV discovery/playback broken. Preserve the Go backend for desktop while the mobile build loads a versioned `/catalog/channels.v1.json` generated at build time from curated India entries. Radio already has a bundled station snapshot and direct audio URLs; select a tested India sample for the launch catalog.
2. For each published entry, keep a stable ID, source URL/provenance, display metadata, known territory or access limits, direct HTTPS media URL, expected format/codec, last successful playback timestamp, and fallback state. List publicly accessible free streams for the alpha after a source and playback check; prioritize official broadcaster endpoints. Remove challenged, paid, encrypted, or clearly restricted links, and provide a takedown contact. The existing rights register has zero entries marked approved, so it cannot yet be treated as evidence of permission; it also need not block a clearly labeled community alpha of linked free feeds. A GitHub playlist or HTTP 200 alone does not establish playback quality or artwork reuse rights.
3. Video and radio bytes must flow **from broadcaster to viewer**, not through Cloudflare Pages. No media segments, HLS playlists, or recordings go into the site build or Pages Functions. This means broadcasters see viewer IP addresses and may enforce their own geographic or access rules; disclose this in the privacy notice. A static site cannot provide the current Go proxy’s header rewriting, stream health preflight, or fallback transport. Its curated streams must play directly in target browsers.
4. Test direct TV playback on physical iPhone Safari and Android Chrome in India, plus desktop Safari/Chrome/Edge. Measure HTTPS, CORS for HLS.js/fetch paths, native HLS behavior, codecs, autoplay/user gesture, mixed-content blocks, referer/cookie requirements, first-frame time, and failed-feed recovery. Require a defined pass rate on the **curated** launch catalog before calling the web app a TV service. If direct playback fails for most candidate sources, static-only hosting is insufficient; revisit the architecture and budget rather than routing video through an unreviewed free-tier proxy.
5. Package a manifest and service worker for Home Screen installation. Cache the shell and small versioned catalog, never live segments. Keep on-device preferences/favorites and private playlist imports local. Parse a personal file on the device, never upload its raw URLs or tokens to an OpenWave-operated cloud service, and never merge imported channels into the public catalog. The current desktop route sends a selected URL only to the viewer's local Go process for playback. Browser storage can be cleared by the user or OS, so any later persistence/export feature must clearly handle embedded credentials; do not silently sync. Imported feeds still need direct browser compatibility in a static Home Screen app, and the UI must distinguish their failures from curated entries. Publish a clear unsupported/offline state, a small curated channel count, and an issue/takedown route. Inspect the build on a preview deployment with physical devices, then move it to the stable public address. Do not assume a preview URL is private without an access-control check. This addendum does **not** trigger deployment or domain registration.

**Why provenance and playback checks precede free hosting:** Static delivery solves hosting cost, not viewer experience. A public guide should identify where a free stream came from, where it is known to work, and when it last played on a real device. Its correction/takedown route handles disputed entries. Private playlists are imported by viewers for themselves and are not published by OpenWave. The India launch set may be deliberately small; usefulness should come from reliable, relevant channels rather than a large raw index.
